# Astryx evaluation for Snackpage

> **Status:** research complete; retain the current implementation and consider
> an isolated `/manage-next` proof of concept. This is not a production
> migration decision.

**Research date:** 2026-07-25
**Astryx version evaluated:** `@astryxdesign/core` 0.1.8
**Related roadmap item:** [Astryx-backed manage view](../../ROADMAP.md#astryx-backed-manage-view)

## Decision summary

Astryx is a credible option for a richer bookmark-management interface. Its
Table and component catalog could provide sorting, filtering, selection,
column configuration, menus, tokenized inputs, dialogs, and notifications
without Snackpage implementing every interaction from scratch.

Astryx is not currently a spreadsheet engine. Snackpage would still own cell
editing, validation, commit and cancel behavior, Vim navigation, mutation
serialization, reconciliation, undo, and unknown-outcome safety. Adopting it
would also replace the current no-build frontend model with React 19, StyleX,
an npm production dependency graph, and generated embedded assets.

The appropriate next step is an isolated manage-view prototype with explicit
acceptance gates. The picker should remain vanilla JavaScript. A wholesale
migration is not justified by the current four-field manager.

## What Astryx is

[Astryx](https://astryx.atmeta.com/) is Meta's MIT-licensed, open-source design
system built with React and StyleX. Meta describes roughly 160 components
covering forms, navigation, feedback, data display, tables, and chat. The
patterns incorporate lessons from an internal design system used across more
than 13,000 products, but the public implementation is a new open-source
rebuild rather than the exact implementation running all those products.

At the time of this evaluation, Astryx is beta at version 0.1.8. Its core
package requires React and ReactDOM 19 or newer and StyleX 0.19. Beta releases
have already contained breaking changes, so exact version pinning and an
explicit upgrade process would be required.

## Current Snackpage manager

Snackpage's `/manage` page is a purpose-built editable bookmark table:

- four fields—title, URL, tags, and aliases—are hard-coded in
  `internal/web/assets/manage.js`;
- every visible row contains native labeled inputs;
- filtering shares the picker's relevance admission and ranking rules;
- normal mode provides two-dimensional Vim navigation and command chords;
- edits save on blur, with Enter, Escape, add, delete, and undo behavior layered
  around that transaction boundary;
- a global mutation scheduler and per-row queues prevent reordered writes and
  duplicate draft creation;
- ambiguous network outcomes block further writes rather than risking a retry;
  and
- an extensive Playwright suite covers editing, races, errors, keyboard
  behavior, themes, and mouse interactions.

This implementation is compact and dependency-light, but its table structure,
editors, cursor, and mutation lifecycle are coupled to DOM row nodes. Adding
column types or conventional data-table features requires custom work.

The current runtime model is intentionally small:

- the Go binary embeds HTML, CSS, and vanilla JavaScript;
- Node and Playwright are development-only;
- there is no production frontend compilation step;
- scripts and styles are same-origin under a strict Content Security Policy;
  and
- eighteen bundled themes override the existing semantic-ish CSS variables.

See the current [frontend architecture](../../ARCHITECTURE.md#6-frontend-model).

## Capability comparison

| Area | Snackpage today | Astryx 0.1.8 | Consequence |
|---|---|---|---|
| Runtime | Embedded vanilla JS and CSS | React 19, StyleX, theme CSS | Adds a production frontend toolchain |
| Table definition | Four hard-coded fields | Data and column schema | Easier to add and configure columns |
| Table features | Filter and sticky layout | Sort, filter, paginate, select, resize, configure, group, expand, tree, and context actions | Substantial improvement for record management |
| Editing | Native inputs with save-on-blur | Custom content through `renderCell` | Snackpage must design the edit lifecycle |
| Navigation | Application-specific 2D Vim cursor | General focus/accessibility primitives | Vim and spreadsheet navigation remain ours |
| Selection | One active cell | Row selection plugin | No built-in cell or range selection |
| Clipboard and fill | None | None found | Requires custom behavior or another grid |
| Undo and reconciliation | Application-owned and tested | Not a Table concern | Existing controller logic must be preserved |
| Large data | Browser DOM rows | Pagination; virtualization remains open | Fine for current scale, uncertain for very large sets |
| Components | Purpose-built controls | Broad component catalog | Useful if management expands beyond text fields |
| Themes | 18 Snackpage themes | Astryx theme system | Requires a token adapter or rebuilt themes |

## Astryx Table: useful capabilities

The public Table API and plugin types include:

- controlled sorting and filtering;
- pagination;
- row selection and selection state;
- column visibility, ordering, resizing, and sticky columns;
- grouped rows and tree data;
- row expansion, row status, and row indices;
- context actions; and
- a public plugin transformation pipeline.

The base implementation renders semantic native table elements. That is a
strong starting point for a record-management screen and avoids an entirely
`div`-based grid.

References:

- [Table documentation](https://github.com/facebook/astryx/blob/main/packages/core/src/Table/Table.doc.mjs)
- [Table exports](https://github.com/facebook/astryx/blob/main/packages/core/src/Table/index.ts)
- [Table plugin and type API](https://github.com/facebook/astryx/blob/main/packages/core/src/Table/types.ts)
- [Base table implementation](https://github.com/facebook/astryx/blob/main/packages/core/src/Table/BaseTable.tsx)

Astryx's wider catalog would also make richer bookmark fields easier to
prototype. Relevant controls include TextInput, Tokenizer, Selector,
PowerSearch, ContextMenu, AlertDialog, Toast, Toolbar, and CommandPalette.

## Spreadsheet capability gaps

A review of the complete public Table exports, documentation, types, and source
found no built-in:

- editable-cell state or commit protocol;
- cell or range selection;
- arrow-key cell navigation;
- multi-cell clipboard copy and paste;
- fill handle;
- formula engine;
- spreadsheet undo and redo; or
- row or column virtualization.

`renderCell` can host an input, but that makes editing an application concern.
Snackpage would need to manage draft state, validation, focus, commit, cancel,
accessibility, keyboard conflicts, mutation state, and rerenders.

The public roadmap corroborates several of these gaps:

- [Table feature tracker #3639](https://github.com/facebook/astryx/issues/3639)
- [Row virtualization #3942](https://github.com/facebook/astryx/issues/3942)
- [Column virtualization #3943](https://github.com/facebook/astryx/issues/3943)
- [Keyboard and pointer row navigation #3952](https://github.com/facebook/astryx/issues/3952)

Consequently, Astryx should be evaluated as a design system and data-table
foundation. Package descriptions or keywords such as "spreadsheet" should not
be interpreted as Excel-like behavior in the current implementation.

## Accessibility and browser support

Positive foundations include native table semantics, ARIA selection state,
focusable horizontal scrolling, keyboard-operable column resizing, and
WAI-ARIA-style patterns across menus, tabs, toolbars, and tree controls.
Astryx also has automated axe-based auditing.

Important qualifications:

- keyboard row navigation is still open roadmap work;
- editable-cell accessibility would remain Snackpage's responsibility;
- no public VPAT or complete WCAG conformance report was found; and
- the public audit script reports violations but does not by itself establish
  conformance.

Astryx documents these browser tiers:

- full fidelity: Chrome and Edge 125+, Safari 26+, Firefox 147+;
- functional: Chrome and Edge 114+, Safari 17+, Firefox 125+.

On the functional tier, controls that depend on CSS anchor positioning can open
away from their trigger. The table itself should be functional, but filters,
selectors, and context menus need explicit Safari 17–25 testing.

## Build, delivery, and size

The supported integration path uses npm packages, precompiled CSS, React, and a
theme provider. Source builds can improve StyleX tree-shaking and CSS-layer
control, but add Babel, PostCSS, or Vite configuration.

Snackpage cannot sensibly use Astryx from a runtime CDN:

- its Content Security Policy permits only same-origin scripts and styles;
- a runtime dependency would weaken offline and release reproducibility; and
- the Go binary is expected to contain the complete UI.

An experiment should generate hashed JavaScript and CSS before `go build`, then
embed those artifacts. The project would need to decide whether release
artifacts are committed or reproducibly generated in every build environment.
Dependencies and licenses would need exact lockfiles and `NOTICE` updates.
Runtime theme style injection should be avoided; compile a Snackpage theme to
static CSS instead.

Local production-mode bundle probes provide an order-of-magnitude comparison:

| Probe | Approximate gzip size |
|---|---:|
| Current manage route's principal JS and CSS | 28 KB |
| React plus Astryx Table and static CSS | 126 KB |
| Rich Astryx table/component prototype | 345–370 KB |
| Complete Astryx UMD JS alone, before React | 229 KB |

These are comparative measurements, not a final performance budget. Exact
imports, theme strategy, code splitting, and source-build configuration will
change the result. Because Snackpage is served over loopback, download latency
is less important than startup, memory, build complexity, and maintainability.

## Recommended proof of concept

### 1. Extract framework-independent behavior

Create a bookmark-ID-based controller for load, create, update, delete, undo,
pending state, server normalization, and unknown outcomes. Define a column
schema with parsing, formatting, validation, search, and editor metadata.
Express Vim commands in row and column IDs instead of DOM elements.

These changes are useful even if Astryx is rejected.

### 2. Build an isolated route

Create `/manage-next` or a development-only laboratory page. Do not replace
`/manage` during evaluation and do not convert the picker.

Use:

- Astryx Table with sorting, resizing, column settings, and selection;
- TextInput or Tokenizer editors through `renderCell`;
- explicit Enter-to-commit and Escape-to-cancel transactions;
- AlertDialog or ContextMenu for destructive actions;
- Toast for confirmed outcomes; and
- a statically compiled Snackpage theme.

### 3. Verify the difficult behavior

The prototype must demonstrate:

- serialized edits and draft creation;
- deletion and undo after pending edits;
- visible validation and server errors;
- blocking after an unknown outcome;
- stable selection across sorting and filtering;
- complete Vim navigation without collisions inside editors;
- keyboard and mouse operation in Chromium, Firefox, and WebKit;
- meaningful editable-grid accessibility;
- CSP-clean execution with no runtime network requests; and
- representative and 1,000-row performance.

### 4. Make an explicit decision

Adopt Astryx for `/manage` only if the prototype materially reduces the cost of
planned features and its maintenance/build cost is acceptable. Otherwise keep
the existing view and apply the controller and column-schema refactor to the
vanilla implementation.

If the desired product becomes an Excel-like spreadsheet, conduct a separate
evaluation of dedicated grid engines. Astryx may still provide surrounding
forms, dialogs, menus, and visual tokens, but should not be expected to supply
spreadsheet mechanics.

## Re-evaluation triggers

Review this decision when any of the following occurs:

- Astryx reaches a stable release;
- row and column virtualization ship;
- keyboard row navigation ships;
- the manager gains multiple typed columns, bulk actions, saved views, or
  additional administration screens; or
- the current manager's custom table code becomes a recurring delivery
  bottleneck.
